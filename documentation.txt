VI. ABSTRACT
============
RetailFlow is a comprehensive, web-based retail management and Point of Sale (POS)
application designed to streamline the day-to-day operations of small to medium-sized
retail businesses. The system replaces manual, paper-based billing and inventory
tracking with a fast, secure, and modern digital interface accessible from any web
browser. It employs a full-stack JavaScript architecture: React.js (with Vite) for
the Single Page Application (SPA) frontend, Node.js and Express for the REST API
backend, and a lightweight, zero-configuration SQLite database for persistent data
storage. Central to the system is a three-tier role-based access control model
distinguishing Managers, Shop Owners, and Employees — each with their own tailored
dashboard and access permissions. Key capabilities include secure JWT-based login,
multi-shop administration, real-time product inventory tracking, an interactive
cart-based Point of Sale checkout, auto-generated bill numbers, customer detail
capture, and analytical dashboards powered by Chart.js. The system was designed to
be deployable on low-cost cloud infrastructure (Firebase Hosting + Render) and
requires no external database server, making it uniquely accessible to small business
operators with limited IT resources.

CHAPTER 1: INTRODUCTION
========================

1.1 PROJECT SUMMARY
--------------------
RetailFlow is a secure, browser-based retail management platform that unifies Point
of Sale (POS) billing, inventory control, employee administration, and sales analytics
into one centralized system — eliminating the inefficiency of paper-ledger bookkeeping
and disconnected cash registers faced by small retail businesses.

The application serves three distinct user roles: a Manager who oversees the entire
system and creates shops, an Owner who manages one assigned shop including its staff
and products, and Employees who carry out daily transactions through the POS checkout
interface. All roles access the system through the same secure login page, after which
they are automatically redirected to their role-specific dashboard.

The system is built with a React + Vite frontend and a Node.js + Express backend
communicating through a RESTful API. Data is persisted in an SQLite database file,
removing the need for a separate database server process. JWT tokens are used for
stateless, secure session management.

1.2 PURPOSE
-----------
The purpose of this project is to develop a practical, deployable, and cost-effective
digital solution for Indian small-format retail shops (kirana stores, general stores,
etc.) that struggle with:

  - Inaccurate manual stock tracking that leads to out-of-stock or overstock situations.
  - Slow, manual billing that reduces checkout throughput.
  - Lack of sales analytics and reporting for informed business decisions.
  - No centralized control mechanism for multi-staff retail operations.

RetailFlow directly addresses these pain points by automating billing, tracking
inventory in real time, and providing role-specific dashboards with visual analytics.

1.3 OBJECTIVE
-------------
The specific objectives of the RetailFlow project are:

  1. Develop a secure, multi-role authentication system distinguishing Managers,
     Owners, and Employees.
  2. Implement role-specific dashboards with appropriate data access and controls
     for each role.
  3. Build a dynamic Point of Sale (POS) interface enabling employees to quickly
     build a cart, apply customer details, and complete a sale.
  4. Automate inventory deduction upon sale completion using database transactions
     to prevent race conditions.
  5. Provide real-time graphical sales analytics (line charts and KPI cards)
     for Owner dashboards.
  6. Implement a persistent billing and sales history log with unique
     auto-generated bill numbers.
  7. Enable shop Owners to manage their employee roster (adding and removing
     employee accounts).
  8. Enable the Manager to provision new shops and assign shop owners.
  9. Include a Settings module for users to update their own profile and credentials.

1.4 SCOPE
---------
WHAT RETAILFLOW CAN DO:
  - Multi-shop provisioning via the Manager role.
  - Owner-level management: add/remove employee accounts, add/edit/delete products.
  - Employee POS checkout: product search, quantity selection, cart management,
    customer capture, and bill generation.
  - Automatic stock deduction from inventory upon every completed sale.
  - Low-stock alerts (products with quantity below 10 units).
  - Auto-generated unique bill numbers (format: BILL-XXXXXXXX).
  - Sales history retrieval; owners/managers see all sales, employees see their own.
  - User profile and password self-service via the Settings page.
  - JWT-based 24-hour session tokens, with automatic redirect to login on expiry.
  - Deployable to Firebase Hosting (frontend) and Render (backend API).

WHAT RETAILFLOW CANNOT DO (CURRENT VERSION):
  - Integration with physical barcode scanners or receipt printers.
  - Multi-currency support or regional tax (GST) calculation on invoices.
  - Vendor/supplier purchase order management.
  - Customer loyalty or rewards programs.
  - Offline mode (requires active network connection to the backend API).
  - Export sales data to Excel or PDF directly from the interface.

1.5 TECHNOLOGY AND LITERATURE REVIEW
--------------------------------------
RetailFlow's technology stack is composed entirely of modern, open-source JavaScript
ecosystem components.

FRONTEND:
  - React.js (v18): Component-based UI rendering with hooks. Allows declarative,
    state-driven views.
  - Vite: Ultra-fast development server and optimized production bundler. Proxies
    /api/* requests to the backend during development.
  - Tailwind CSS: Utility-first CSS framework for rapid, consistent styling.
  - React Router (v6): Client-side routing for the SPA with protected route handling.
  - Chart.js + react-chartjs-2: Canvas-based charting library for line charts
    and doughnut charts in dashboards.
  - Context API (React): Lightweight global state management for auth state,
    app data, and toast notifications.

BACKEND:
  - Node.js: JavaScript runtime for server-side logic.
  - Express.js: Minimalist HTTP framework for building structured RESTful API routes.
  - JSON Web Tokens (JWT): Stateless token-based authentication; tokens embed
    user ID, name, and role. Expire after 24 hours.
  - bcryptjs: Industry-standard password hashing with salt rounds (cost factor 10)
    to prevent rainbow table attacks.
  - Helmet.js: Sets secure HTTP headers (Content-Security-Policy, X-Frame-Options).
  - Morgan: HTTP request logger middleware for debugging.
  - CORS: Configurable Cross-Origin Resource Sharing policy; locked to frontend origin.
  - dotenv: Manages environment variables (PORT, JWT_SECRET, DATABASE_PATH,
    FRONTEND_ORIGIN).

DATABASE:
  - SQLite (via better-sqlite3): Serverless relational database stored as a single
    file (retailflow.db). Supports WAL (Write-Ahead Logging) mode and foreign key
    constraints. No separate database server is required.
  - UUID (v4): Universally Unique Identifiers used for all primary keys.

LITERATURE REVIEW:
  The design of RetailFlow draws inspiration from established Point of Sale principles
  described in "Retail Management: A Strategic Approach" (Berman & Evans) and modern
  RESTful API design guidelines from Roy Fielding's architectural constraints paper.
  The role-based access control (RBAC) model is consistent with NIST SP 800-207
  Zero Trust security principles, wherein each role gets minimum necessary privileges.

2.1.1 PROJECT DEVELOPMENT APPROACH AND JUSTIFICATION
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
An Agile (iterative and incremental) development approach was chosen for RetailFlow.
The system was built in clearly defined sprints:

  Sprint 1 — Project setup, database schema definition, seed data, and authentication.
  Sprint 2 — Products CRUD API and frontend product management for Owner role.
  Sprint 3 — POS Cart component, sale submission, and stock deduction logic.
  Sprint 4 — Sales history, bills history, and Owner dashboard analytics (charts).
  Sprint 5 — Manager dashboard (shop and owner management), User Management page.
  Sprint 6 — Settings page (profile and password update), UI polishing, deployment.

Justification: Agile is appropriate because the UI requirements (dashboards, cart
interactions) were not fully clear upfront. Iterative delivery allowed stakeholder
review at each stage and early identification of integration issues between the
React frontend and Express API.

CHAPTER 4: SYSTEM ANALYSIS
===========================

4.1 STUDY OF CURRENT SYSTEM
-----------------------------
Traditional small-format retail shops in India typically rely on:

  - Manual paper ledgers for daily sales recording.
  - Standalone cash registers with no digital record trail.
  - Oral or manual stock management with periodic physical counts.
  - No mechanism for remote monitoring of store performance by the owner.
  - No historical sales analysis, making it impossible to identify top-selling
    products or slow business days.

4.2 PROBLEM AND WEAKNESSES OF CURRENT SYSTEM
----------------------------------------------
  1. Calculation Errors: Manual arithmetic during billing leads to over-charging
     or under-charging customers.
  2. Inventory Blind Spots: Inability to track real-time stock levels causes
     out-of-stock scenarios and lost sales.
  3. No Audit Trail: Lost paper receipts mean no record of transactions, enabling
     theft or billing disputes.
  4. No Analytics: Owners cannot make data-driven decisions such as which products
     to reorder or discount.
  5. Slow Checkout: Manual billing slows the checkout queue, reducing customer
     satisfaction.
  6. No Multi-Staff Visibility: Owners cannot monitor employee sales performance
     or daily activity.

4.3 REQUIREMENTS OF NEW SYSTEM
--------------------------------

4.3.1 FUNCTIONAL REQUIREMENTS
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
  FR-01 : The system shall authenticate users with email and password.
  FR-02 : The system shall issue and validate JWT tokens with a 24-hour expiry.
  FR-03 : The system shall redirect authenticated users to their role-specific dashboard.
  FR-04 : The Manager role shall be able to create new shops and assign owners.
  FR-05 : The Owner role shall be able to add, edit, and delete products in their shop.
  FR-06 : The Owner role shall be able to create and remove employee accounts.
  FR-07 : The Employee role shall be able to search and select products to add to cart.
  FR-08 : The system shall capture customer details (name and phone) at time of sale.
  FR-09 : The system shall deduct product stock quantities upon a successful sale.
  FR-10 : The system shall generate a unique bill number (BILL-XXXXXXXX) for each sale.
  FR-11 : The system shall display past sales filtered by role (all sales for Owner
          and Manager; own sales only for Employee).
  FR-12 : The system shall alert users when any product's stock drops below 10 units.
  FR-13 : Users shall be able to update their own name, email, phone, and password
          via the Settings page.

4.3.2 NON FUNCTIONAL REQUIREMENTS
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
  NFR-01 : Security — Passwords shall be stored using bcrypt (cost factor 10);
           plaintext passwords are never stored in the database.
  NFR-02 : Performance — API responses for product listing and sale submission
           shall complete in under 300ms on a local network.
  NFR-03 : Availability — The system shall depend only on services that can be
           hosted for free (Firebase and Render free tiers).
  NFR-04 : Scalability — The REST API architecture supports future migration from
           SQLite to PostgreSQL without frontend changes.
  NFR-05 : Usability — The Employee POS interface shall allow completing a checkout
           in under 5 interactions.
  NFR-06 : Maintainability — Backend routes are organized into separate files per
           domain (auth, products, sales, users, shops).

  2. POST request to /api/auth/email-login
  3. SELECT user WHERE email matches
  4. bcrypt.compare(inputPassword, storedHash)
  5. If match: jwt.sign({ id, name, role }, JWT_SECRET, expiresIn: 24h)
  6. Return token and user object { id, name, role, email }
  7. Frontend stores token in localStorage
  8. Navigate to role-specific route

4.12 SELECTION OF HARDWARE AND SOFTWARE AND JUSTIFICATION
----------------------------------------------------------
  React.js + Vite:
    React provides a component model ideal for complex, interactive UI like the
    POS cart. Vite is chosen over Create React App for its faster hot module
    replacement and build speed.

  Node.js + Express:
    Allows using a single language (JavaScript) across both frontend and backend,
    reducing context switching and enabling code sharing.

  SQLite (better-sqlite3):
    Zero-configuration, file-based relational database. Chosen because no separate
    database server is needed, making it ideal for cost-constrained deployments.

  JWT (JSON Web Tokens):
    Stateless authentication that avoids server-side session storage, simplifying
    future horizontal scaling.

  Tailwind CSS:
    Utility-first classes allow rapid, consistent UI development without writing
    custom CSS files.

5.1.1 METHOD PSEUDO CODE

-- AUTHENTICATION (backend/routes/auth.js) --

FUNCTION emailLogin(email, password):
    user = DB.query("SELECT * FROM users WHERE LOWER(email) = ?", email)
    IF user is NULL THEN
        RETURN 401 "No account found for this email"
    isMatch = bcrypt.compare(password, user.password)
    IF NOT isMatch THEN
        RETURN 401 "Incorrect password"
    token = jwt.sign({ id, name, role }, JWT_SECRET, expiresIn: "24h")
    RETURN 200 { token, user }


-- POS SALE SUBMISSION (backend/routes/sales.js) --

FUNCTION createSale(items, customerName, customerPhone, userId):
    totalAmount = 0
    BEGIN TRANSACTION
        FOR EACH item IN items:
            product = DB.query("SELECT * FROM products WHERE id = ?", item.productId)
            IF product is NULL THEN THROW "Product not found"
            IF item.quantity > product.quantity THEN THROW "Insufficient stock"
            totalAmount += product.price * item.quantity
            DB.execute("UPDATE products SET quantity = quantity - ? WHERE id = ?",
                        item.quantity, product.id)

        billNumber = "BILL-" + LAST_8_DIGITS(Date.now())
        saleId = uuid()
        DB.execute("INSERT INTO sales (...) VALUES (...)",
                    saleId, billNumber, items_JSON, totalAmount, ...)
    COMMIT TRANSACTION
    RETURN 201 newSaleRecord

5.2 DATABASE DESIGN/DATA STRUCTURE DESIGN
------------------------------------------

5.2.1 MAPPING OF ER DIAGRAMS INTO TABLES
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
All ER entities map directly to SQLite relational tables with UUID primary keys
and foreign key constraints enforced via PRAGMA foreign_keys = ON. Shop is the
central anchor entity. Users reference shops via shop_id. Products reference
shops via shop_id with CASCADE DELETE, meaning that deleting a shop automatically
removes its products. Sales reference both shops (CASCADE) and users (SET NULL on
user delete), preserving historical sale records even if an employee is removed.

5.2.2 NORMALIZATION
~~~~~~~~~~~~~~~~~~~~
The shops, users, and products tables conform to Third Normal Form (3NF):
  - Each table has a single primary key (UUID).
  - No partial dependencies exist (all PKs are single-column).
  - No transitive dependencies exist (shop details are in the shops table,
    not repeated in users or products).

The sales table uses a controlled denormalization: line items are stored as a JSON
array within the items TEXT column. This is a deliberate architectural decision to
preserve an immutable receipt snapshot — if a product is later renamed or deleted,
its original sale record remains historically accurate.

5.3.2 ACCESS CONTROL AND SECURITY
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
  - All API routes (except /api/auth) are protected by the authMiddleware function
    which validates the Bearer JWT token in the Authorization header.
  - Product create, edit, and delete routes are additionally guarded by the
    ownerOnly middleware which checks the decoded user role from the token.
  - The frontend uses a ProtectedRoute React component that reads the auth token
    from localStorage; if missing or expired, it redirects to the login page.
  - CORS is locked to the configured FRONTEND_ORIGIN (default: localhost:5173);
    requests from unlisted origins are rejected.
  - Helmet.js sets HTTP security headers on every API response.
  - Passwords are never returned in any API response; SELECT queries explicitly
    exclude the password column from all user-facing endpoints.

6.3 SECURITY FEATURES
-----------------------
  1. bcrypt Password Hashing:
     All passwords are hashed with bcrypt (saltRounds = 10) before storage.
     Plaintext passwords never persist in the database.

  2. JWT Authentication:
     All non-public API endpoints require a valid, non-expired JSON Web Token
     passed in the Authorization: Bearer header.

  3. Role Enforcement:
     Server-side middleware (ownerOnly, managerOnly) checks the user role extracted
     from the JWT before processing any sensitive operations.

  4. HTTP Security Headers:
     Helmet.js automatically sets headers including X-Content-Type-Options,
     X-Frame-Options, and Content-Security-Policy on every response.

  5. CORS Whitelisting:
     Only requests from the configured FRONTEND_ORIGIN are accepted. Cross-origin
     requests from unlisted domains are automatically rejected.

  6. Environment Variable Secrets:
     JWT_SECRET and DATABASE_PATH are stored in environment variables, never
     hardcoded. The .env file is listed in .gitignore and never committed to Git.

  7. Input Validation:
     All POST and PUT API routes validate required fields, data types, and value
     ranges before writing anything to the database.

6.4 CODING STANDARDS
----------------------
  Language:
    JavaScript (ES2022) throughout — both frontend (JSX) and backend (CommonJS).

  Linter:
    ESLint configured at the repo root (eslint.config.js) covering both frontend
    and backend source files.

  Naming Conventions:
    camelCase for functions and variables.
    PascalCase for React components and class names.

  File Organization:
    Backend routes are split by domain (auth, products, sales, users, shops).
    Frontend follows a pages / components / context / services / utils structure.

  Error Handling:
    All Express route handlers are wrapped in try-catch blocks. A global error
    handler in index.js catches any unhandled errors.

  Database Access:

    prepare().run() / get() / all() methods to prevent SQL injection attacks.

    inline comments throughout the codebase.

CHAPTER 8: CONCLUSION AND DISCUSSION

8.1 SELF ANALYSIS OF PROJECT VIABILITIES
------------------------------------------
RetailFlow successfully demonstrates that a full-featured retail management system
can be built using entirely open-source technology at zero runtime cost. All 13
functional requirements defined in Chapter 4 have been implemented and validated.
The role-based access model is clean and extensible. The use of SQLite provides
sufficient database capability for single-shop to small-multi-shop operations
without infrastructure overhead.

The system is viable for deployment and practical use by a small retail business
today. Its architecture is also sound enough to support a migration path to a more
scalable database such as PostgreSQL if user load demands grow.

8.2 PROBLEM ENCOUNTERED AND POSSIBLE SOLUTIONS
------------------------------------------------
PROBLEM 1 — CART STATE LOST ON BROWSER REFRESH:
  Encountered:
    During employee checkout, accidentally refreshing the browser cleared the
    cart entirely, losing all selected items.
  Solution Implemented:
    React state was combined with a sessionStorage-based cart persistence
    mechanism to survive page refreshes within the same browser session.

PROBLEM 2 — RACE CONDITION RISK ON CONCURRENT SALES:
  Encountered:
    Theoretically, two employees checking out the same product simultaneously
    could both pass the stock check before either of them updates the quantity.
  Solution Implemented:
    The entire sale creation process (stock validation, stock deduction, and
    INSERT into sales) was wrapped in a db.transaction() block using
    better-sqlite3's atomic transaction API, preventing race conditions at
    the database level.

PROBLEM 3 — MODULE NOT FOUND ERRORS AFTER NPM INSTALL:
  Encountered:
    Helmet and other dependencies failed to resolve when a separate node_modules
    folder existed inside the backend directory. The npm workspace setup requires
    a single root-level install.
  Solution Implemented:
    All nested node_modules folders inside backend and frontend were deleted.
    Dependencies resolved correctly via the single root-level npm install command.

8.3 SUMMARY OF PROJECT WORK
-----------------------------
RetailFlow was designed, developed, tested, and deployed as a complete retail
management SPA and API system. It covers user authentication, multi-role access
control, product management, POS billing, sales analytics, employee management,
and self-service account settings. The system follows modern web development
best practices including JWT security, bcrypt hashing, RESTful API design,
atomic database transactions, input validation, and CORS protection.


CHAPTER 9: LIMITATION AND FUTURE ENHANCEMENT
=============================================

CURRENT LIMITATIONS:
  1. SQLite is a file-based database. It is not suitable for high-concurrency
     multi-server deployments. A migration to PostgreSQL would be needed for
     enterprise-level scale.
  2. The system requires an active network connection. If the backend server
     is unreachable, the frontend shows network errors and no data loads.
  3. The system generates and stores bill records internally but does not
     produce a printable thermal receipt or downloadable PDF invoice.
  4. Prices are stored as-is; no GST, VAT, or discount calculation is applied
     to sales totals at the time of billing.
  5. Product entry requires manual search; no barcode scanner hardware
     integration exists in the current version.
  6. The system is calibrated for INR (Indian Rupee) only; no multi-currency
     support is available.

FUTURE ENHANCEMENTS:
  1.  Migrate the database to PostgreSQL for better concurrency and cloud hosting.
  2.  Add thermal receipt printer support via browser WebUSB or WebSerial APIs.
  3.  Implement PDF invoice generation for each completed sale.
  4.  Add GST calculation and per-line tax columns to the invoice.
  5.  Add barcode scanning via a webcam-based library such as QuaggaJS.
  6.  Implement a customer loyalty points and rewards system.
  7.  Add a purchase order and vendor management module for stock replenishment.
  8.  Develop a React Native mobile app for on-the-go owner analytics.
  9.  Add email and SMS customer bill notifications via Twilio or SendGrid.
  10. Export sales data to Excel (XLSX) or PDF format for accounting purposes.

API  -> SRV  : HTTP POST with Authorization: Bearer <JWT>

SRV  -> AUTH : Verify JWT token
AUTH -> SRV  : Return decoded { id, name, role }

loop For each item in items[]
  SRV  -> DB : SELECT * FROM products WHERE id = item.productId
  DB   -> SRV : Return product record
  SRV  -> SRV : Check item.quantity <= product.quantity
  SRV  -> SRV : Accumulate totalAmount
end

SRV  -> DB : BEGIN TRANSACTION
loop For each item
  SRV -> DB : UPDATE products SET quantity = quantity - item.qty
end
SRV  -> DB : INSERT INTO sales (billNumber, items JSON, totalAmount, ...)
SRV  -> DB : COMMIT TRANSACTION
DB   -> SRV : Return new sale record

SRV  -> API  : 201 Created — { id, billNumber, total, items }
API  -> CART : Resolve response
CART -> EMP  : Show success toast notification
CART -> EMP  : Clear cart

USR -> UI  : Enter email and password
USR -> UI  : Click "Sign In"

UI  -> API : POST /api/auth/email-login\n{ email, password }
API -> SRV : HTTP POST (no auth header needed)

SRV -> DB  : SELECT * FROM users WHERE LOWER(email) = ?
DB  -> SRV : Return user record (or NULL)

alt User not found
  SRV -> API : 401 — "No account found for this email"
  API -> UI  : Reject with error message
  UI  -> USR : Display error on Login page
else User found
  SRV -> SRV : bcrypt.compare(inputPassword, user.password)

  alt Password does not match
    SRV -> API : 401 — "Incorrect password"
    API -> UI  : Reject with error message
    UI  -> USR : Display error on Login page
  else Password matches
    SRV -> JWT : jwt.sign({ id, name, role }, JWT_SECRET, expiresIn: 24h)
    JWT -> SRV : Return signed token string

    SRV -> API : 200 OK — { token, user: { id, name, role, email } }
    API -> UI  : Resolve with token and user object
    UI  -> UI  : Store token in localStorage
    UI  -> USR : Navigate to role-specific dashboard\n(/manager | /owner | /employee)
  end
end
